Five minutes. One PR. Whatever agent you already use.

<Note>
  **Research Preview** — Genie is experimental. Things will break, APIs will change, and we want your feedback. Honest feedback, not polite feedback. [Tell us on Discord](https://discord.gg/automagik).
</Note>

<Steps>
  <Step title="Install Genie">
    Run the bootstrap script (see the full [Installation guide](/genie/installation) for alternatives). It installs the signed CLI, then the skills and the saved-workflow catalog into the agent homes it detects.

    ```bash
    curl -fsSL https://raw.githubusercontent.com/automagik-dev/genie/main/install.sh | bash
    ```

    Verify the install:

    ```bash
    genie doctor
    ```

    Expected output:
    ```text
    ✓ genie CLI found
    ✓ authority: standalone
    ✓ skills: claude 19/19 @ v6.x.x
    ✓ skills: agents 19/19 @ v6.x.x
    ```
  </Step>

  <Step title="Choose Your Agent (or don't — we don't care)">
    Genie orchestrates agents. It is not an agent. Use whatever you like — we have opinions about orchestration, not about your vendor choices.

    | Agent | Setup | Notes |
    |-------|-------|-------|
    | **Claude Code** | Nothing to do | Skills become slash commands, plus the saved-workflow catalog in `~/.claude/workflows` |
    | **Codex** | Nothing to do | OpenAI's agent. Reads Genie's skills from the shared `~/.agents/skills` home |
    | **Goose, Windsurf, and the rest** | Nothing to do | Any agent skills.sh supports gets the same skills in its own skill home |
    | **Custom (BYOA)** | Nothing to do | Any CLI agent that reads a skills directory. Seriously, anything. |

    There is nothing per-agent to configure: Genie installs to the agents it **detects**, and the skills are
    runtime-neutral, so the same body works everywhere.

    <Tip>
      **You're never locked in.** Switch agents mid-project or mix them on the same wish.
      See the [architecture overview](/genie/architecture/overview) if you're the kind of person who builds their own tools.
    </Tip>
  </Step>

  <Step title="Scaffold the repository">
    From inside the repository you want to work in:

    ```bash
    genie init
    ```

    It scaffolds the per-repo state and retires the historical MCP registrations Genie can prove it owns — backup-first,
    leaving every unrelated key byte-for-byte intact.

    ```text
    .genie/
      wishes/       → WISH.md per slug, tracked in git
      brainstorms/  → DESIGN.md per slug, tracked in git
      INDEX.md      → the hand-written index
      roadmap.json  → the canonical board snapshot, tracked in git
      genie.db      → tasks, lanes, dependency edges (SQLite, gitignored)
    ```

    Then open your agent in that directory. The skills are already in its skill home — nothing to paste, nothing to
    register.
  </Step>

  <Step title="Brainstorm Your First Idea">
    Got something you want to build? Tell the brainstorm skill about it:

    ```text
    /brainstorm Add a dark mode toggle to the settings page
    ```

    It'll walk you through the thinking you'd do anyway — but faster:

    <AccordionGroup>
      <Accordion title="Scope" icon="crosshairs">
        What's in, what's out. The brainstorm skill pushes you to name both edges before you write a line of code.
      </Accordion>
      <Accordion title="Constraints" icon="link">
        Dependencies, breaking changes, hidden invariants. If something is load-bearing, it gets called out here instead of surfacing in review.
      </Accordion>
      <Accordion title="Design" icon="compass-drafting">
        Approach and tradeoffs. This is the "why this way" that your future self will thank you for.
      </Accordion>
      <Accordion title="Readiness" icon="circle-check">
        Is this crisp enough to actually build? If not, the brainstorm keeps probing until it is.
      </Accordion>
    </AccordionGroup>
  </Step>

  <Step title="Create a Wish">
    When the brainstorm crystallizes, turn it into something agents can execute:

    ```text
    /wish
    ```

    <Note>
      For **one decided task**, `/wish` skips the plan entirely: it admits the task, builds it in its own worktree, gates it, has a different agent review the commit, and opens a merge-ready PR. The walkthrough below shows the other path — work that is bigger than one task, which becomes a `WISH.md` for `/work`.
    </Note>

    This produces a `WISH.md` — the contract between you and your agents:
    - Summary and scope (so nobody wanders off)
    - Acceptance criteria (checkboxes — unambiguous "done")
    - Execution groups (parallelizable work units)
    - Validation commands (proof it works)
  </Step>

  <Step title="Execute and Ship">
    Let the agents do the work:

    ```text
    /work
    ```

    When they're done, validate:

    ```text
    /review
    ```

    **SHIP** → PR created. **FIX-FIRST** → fix loop runs automatically. You don't babysit either way.
  </Step>
</Steps>

## What just happened?

You typed four slash commands and got a pull request. Your agent did the actual work. Here's what it looked like:

```bash /brainstorm

  ✓ Toggle component in settings

  ✓ Must avoid FOUC on page load
  ✓ Existing component tests must pass

Design crystallized → ready for /wish

```

</Frame>

| Step | Skill | Output |
|------|-------|--------|
| Explore | `/brainstorm` | Design document |
| Deliver one task | `/wish` | A merge-ready PR (no plan needed) |
| Plan bigger work | `/wish` (plan entry) | WISH.md with criteria |
| Build | `/work` | Code changes across execution groups (tracked as tasks in `.genie/genie.db`) |
| Validate | `/review` | SHIP, FIX-FIRST, or BLOCKED verdict |
| Ship | PR created | Ready for you to merge (agents don't push to production — that's your job) |

<Note>
  Under the hood, Genie tracks every task, lane, and dependency edge in **one per-repo SQLite file** — no daemon, no
  server, no port. `genie board` renders the kanban live by query, and `genie task status <id>` shows one card's detail
  and stage log. The plan documents themselves stay in git, so you review them like code.
</Note>
