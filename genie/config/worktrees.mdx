Work on a wish happens in an isolated working copy, so two execution groups can touch the same repository without
fighting over the index. The **orchestrator** arranges that isolation, following the dispatch contract for the runtime
it is driving. Genie's own job is narrower and entirely read-only: it answers the question *which branch, from which
base commit, with which ready tasks* — and the answer is one line of JSON.

<Note>
  Genie spawns nothing. There is no daemon, no process registry, and no pane orchestration: `genie context` prints a
  payload and exits, and whatever your orchestrator does with it is its own business.
</Note>

## The Context Contract

```bash
genie context --wish <slug>              # wish branch + every ready task of the wish
genie context --wish <slug> --group <g>  # the composed group branch + that group's ready tasks
genie context                            # no wish: the integration branch and its SHA
```

Each form prints a single line of versioned JSON:

```text
{"version":1,"wish":"<slug>","branch":"wish/<slug>-<group>","base":"<40-hex>","tasks":[{"id":"…","title":"…"}],"group":"<group>"}
{"version":1,"wish":"<slug>","branch":"wish/<slug>","base":"<40-hex>","tasks":[…]}
{"version":1,"branch":"<integration-branch>","base":"<40-hex>","tasks":[]}
```

| Field | Meaning |
|-------|---------|
| `version` | Payload version — consumers pin on it |
| `wish` / `group` | Present only in the scoped forms |
| `branch` | The branch the spawn should live on |
| `base` | The full 40-hex commit the branch is based on — the value that actually crosses the boundary |
| `tasks` | The ready set: the cards with no unmet dependency |

The base SHA is **recorded** the first time a wish resolves it, so every later group of the same wish starts from the
same commit instead of drifting onto whatever the integration branch has become. `--re-resolve` deliberately refreshes
it; `--plan` previews the whole payload without writing anything at all.

<Tip>
  `genie context --wish <slug> --plan` is the safe way to see what a spawn would get. It is also the one lifecycle
  read that still answers when Orca owns the lifecycle authority.
</Tip>

## Where Worktrees Live

The worktrees base is `<GENIE_HOME>/worktrees` — by default `~/.genie/worktrees`.

| Variable | Effect |
|----------|--------|
| `GENIE_HOME` | Relocates **all** global state, the worktrees base included |
| `GENIE_WORKTREES_DIR` | Overrides just the worktrees base |

```bash
export GENIE_HOME=/data/genie             # worktrees go to /data/genie/worktrees
export GENIE_WORKTREES_DIR=/scratch/wt    # or point only the worktrees elsewhere
```

## What the Copies Share

Every linked worktree of one repository shares **one** `.genie/genie.db`, resolved through
`git rev-parse --git-common-dir`. A card created in one worktree is instantly visible in every other — there is no sync
step between worktrees, no per-worktree copy, and nothing to reconcile.

| State | Shared across worktrees? | Why |
|-------|--------------------------|-----|
| Task, lane, and dependency state (`.genie/genie.db`) | Shared | One database per repository, resolved via the common git dir |
| `roadmap.json` — the canonical board snapshot | Per checkout, travels in git | It is a tracked file, so it moves with the branch and merges like code |
| `WISH.md`, `DESIGN.md`, `INDEX.md` | Per checkout, travels in git | Tracked documents; you review them the way you review code |
| Machine-local brainstorm notes | Per checkout | Gitignored scratch work — only the reviewed design travels |
| Git branches and the index | Independent | That is the entire point of the isolation |

<Note>
  Because `genie.db` is shared and `roadmap.json` is tracked, the two can legitimately diverge after a pull or a
  rebase. `genie task sync` three-way reconciles them, and the git hooks run it on pull, merge, rewrite, and
  pre-commit. When both sides moved but only a card's timeline differs, the events are unioned by identity and
  republished — the card conversation is global state.
</Note>

## Cleanup

Worktrees are ordinary git worktrees, so git is the tool that removes them:

```bash
git worktree list
git worktree remove <path>
git worktree prune
```

`genie doctor` observes the worktrees base and reports residue it finds there. `genie doctor --fix` removes only what
it can prove is safe — v4-era residue and worktrees whose work is already merged and whose tree is clean — and refuses
anything ambiguous. Nothing else in Genie deletes a working copy, which is deliberate: uncommitted work is never worth
a tidy directory listing.

## Gotchas

- **One database, many checkouts.** Moving a card in a worktree moves it everywhere. That is the feature, but it does
  mean a stray `genie task move` in a side worktree is not a local experiment.
- **The base SHA is sticky.** Groups of one wish share the recorded base on purpose. If you genuinely want a newer
  base, ask for it with `--re-resolve` rather than deleting state.
- **`genie context` needs an integration branch.** With no local `dev` and no remote HEAD, it refuses and names the
  remedy (`git remote set-head origin -a`) instead of guessing a base.
- **Don't garbage-collect the parent out from under a worktree.** Linked worktrees share the parent's object store;
  pruning it while they exist is how you lose commits that only they reference.
