Genie keeps three kinds of state, and they are deliberately separate:

| Kind | Where | Why there |
|------|-------|-----------|
| **Configuration** | `~/.genie/config.json` | One file, schema-validated, machine-wide |
| **Documents** | `<repo>/.genie/wishes/`, `<repo>/.genie/brainstorms/`, `<repo>/.genie/INDEX.md` | Plain markdown in git — you diff, review, and version them like code |
| **Operational state** | `<repo>/.genie/genie.db` | One SQLite file per repository. No daemon reads it; a command opens it, runs one transaction, and exits |

<Note>
  There is **no PostgreSQL**, no embedded database server, no port to bind, and nothing resident between invocations.
  The v4 pgserve backend was removed in the cutover to the lightweight body.
</Note>

## config.json

**Location:** `~/.genie/config.json` (relocated wholesale by `GENIE_HOME`).

Managed by `genie setup`, read back by `genie config get`, and validated by a Zod schema on every load. An invalid
config falls back to defaults with a warning rather than failing the command.

```json
{
  "version": 2,
  "session": { "name": "genie", "defaultWindow": "shell", "autoCreate": true },
  "terminal": { "execTimeout": 120000, "readLines": 100 },
  "logging": { "tmuxDebug": false, "verbose": false },
  "budgets": { "maxFableCallsPerWish": 3, "maxEscalationsPerGroup": 2 },
  "routing": { "maxAutoEffort": "xhigh", "fableGateMaxAt": 7 },
  "shell": { "preference": "auto" },
  "shortcuts": { "tmuxInstalled": false, "shellInstalled": false },
  "runtime": { "defaultAgent": "auto" },
  "orchestration": { "mode": "standalone" },
  "installMethod": "bun",
  "updateChannel": "latest",
  "setupComplete": true,
  "promptMode": "append"
}
```

### Key sections

<AccordionGroup>
  <Accordion title="orchestration.mode — the lifecycle authority">
    `standalone` (the default, including when the key is absent) or `orca`. This is the **only** thing that decides who
    owns your board state; installing or opening Orca changes nothing on its own. Select it explicitly with
    `genie setup --orchestration-mode <mode>`, never by hand — the setup path probes the runtime and backs the file up
    before it switches.

    An `orchestration.mode` Genie cannot read refuses at exit 2 with its own message, because Genie cannot prove
    `standalone` either. `genie setup --orchestration-mode standalone` repairs it: the original bytes are backed up
    under `~/.genie/backups/orchestration-mode/` first, and every other key it could read is kept.
  </Accordion>

  <Accordion title="budgets — gates may only be tightened">
    Every `budgets.*` key is a conservative default with a schema ceiling (`maxFableCallsPerWish` 10,
    `maxEscalationsPerGroup` 5). A budget bounds how much extra work a gate may authorize before a human is asked, so
    configuration may only **tighten** it. A hand-edited value past the ceiling fails the whole parse, so the resolved
    value is the default and `genie config get` reports `source: default` — never the out-of-range number.

    Skills read these values through the CLI rather than restating them:

    ```bash
    genie config get budgets.maxEscalationsPerGroup
    ```
  </Accordion>

  <Accordion title="updateChannel — stable or dev">
    Canonical values are `latest` (stable) and `dev` (pre-release). Two read-time aliases still parse so configs written
    by older binaries keep working: `next` resolves to `dev`, and the retired `homolog` resolves to `latest` — the
    conservative direction, because silently subscribing a host to less-vetted dev builds would be a regression nobody
    consented to. Neither alias round-trips to disk.
  </Accordion>

  <Accordion title="runtime.defaultAgent">
    `auto` (detect), `claude`, or `codex`. It selects which agent Genie assumes when a command needs one; it never
    installs an agent and never writes into an agent's settings file.
  </Accordion>
</AccordionGroup>

## State storage — one SQLite database

There is exactly **one** database, and it is per-repository: `<repo>/.genie/genie.db`. It runs on Bun's built-in
engine, uses WAL and a `busy_timeout`, and holds tasks, dependency edges, board lanes, wish-group execution state and
the stage log. Its schema is at `user_version = 2`.

Linked worktrees resolve it through `git rev-parse --git-common-dir`, so a task created in one worktree is immediately
visible in another with **no sync step**.

<Note>
  **v6 opens no machine-scope database.** The global `~/.genie/genie.db` existed only to hold the Omni approval queue
  and inbox; with Omni removed there is nothing for it to hold, and the module that owned it is gone. `~/.genie` still
  holds `config.json`, the skills install record, `state-backups/` and `worktrees/` — just no database.
</Note>

### Documents in git

| Document | Location | Tracked |
|----------|----------|---------|
| Wishes | `<repo>/.genie/wishes/<slug>/WISH.md` | Yes |
| Reviewed designs | `<repo>/.genie/brainstorms/<slug>/DESIGN.md` | Yes |
| Index | `<repo>/.genie/INDEX.md` | Yes |
| Other brainstorm notes | `<repo>/.genie/brainstorms/<slug>/` | No — machine-local |
| Board snapshot | `<repo>/.genie/roadmap.json` | Yes — the canonical roadmap |
| The database itself | `<repo>/.genie/genie.db` | No |

`roadmap.json` is the canonical board: `genie task sync` reconciles it against `genie.db` three ways, and git hooks run
it on merge, rewrite, and pre-commit. When both sides moved but only a card's timeline differs, the events are unioned
by identity and republished — the card conversation is global state, not a local view.

## Environment variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `GENIE_HOME` | `~/.genie` | Relocates **all** global state — `config.json`, the skills install record, `state-backups/` and `worktrees/` |
| `GENIE_AGENT_NAME` | — | Worker identity for task claims and stage-log entries; the default for `task checkout --worker` |
| `GENIE_AGENT_ID` | — | Fallback worker identity when `GENIE_AGENT_NAME` is unset; both floor at `cli` |
| `GENIE_WORKTREES_DIR` | `<GENIE_HOME>/worktrees` | Override the worktrees base doctor and review snapshots read |

## Agent skill homes

Genie does not write into any agent's settings file. The one place it puts content inside an agent's configuration is
the agent's **skill home**, and it gets there through the [skills.sh](https://skills.sh) channel — run by the bootstrap
script on first install, and by `genie update` on every update:

| Agent | Skill home |
|-------|------------|
| Claude Code | `~/.claude/skills/` |
| Codex (and every agent that reads the shared home) | `~/.agents/skills/` |
| Goose | `~/.config/goose/skills/` |
| Windsurf | `~/.codeium/windsurf/skills/` |

Genie records what it installed, and where, at `~/.genie/skills-install.json`:

```json
{
  "ref": "v6.260919.1",
  "source": "local:/home/you/.genie/skills",
  "cliVersion": "1.5.23",
  "inventory": ["wish", "work", "review", "..."],
  "agentDirs": ["/home/you/.claude/skills", "/home/you/.agents/skills"],
  "dirDigests": { "/home/you/.claude/skills/wish": "…" },
  "installedAt": "2026-09-19T12:00:00.000Z"
}
```

<Note>
`agentDirs` is a bounded post-install discovery scan of your home directory unioned with the known-homes floor, not a
fixed table — it names every directory the skills CLI actually wrote, and a recorded home that later vanishes is
reported and **kept** in the record rather than dropped. `genie doctor` reads this record to report drift; `genie
uninstall` reads it, and re-verifies `dirDigests`, to decide what it may safely delete. Genie never modifies
`~/.claude/settings.json`.
</Note>

## Saved workflows

Alongside the skills, `genie install` and `genie update` deliver the saved-workflow catalog into Claude Code's user
scope at `~/.claude/workflows/`. A workflow is a script the harness executes for a procedure that is worth running the
same way every time — the `council` deliberation, the documentation audit, the skill-intake sweep. The catalog's
`README.md` is documentation and is never delivered.
