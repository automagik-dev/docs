# Contributing

Genie is built with Bun and TypeScript. This guide covers setting up a development environment, running quality gates, and building plugins. We build in public because that's the only honest way to build developer tools.

## Development Setup

### Prerequisites

| Tool | Version | Purpose |
|------|---------|---------|
| [Bun](https://bun.sh/) | >= 1.3.10 | Runtime, bundler, test runner |
| [git](https://git-scm.com/) | 2.x+ | Version control, worktrees |

Genie spawns no panes and starts no resident processes, so tmux is not required
to build or run it. The skills are plain Markdown: any agent that reads a skills
directory can use them, and no particular agent runtime is a prerequisite for
working on the code. Stable is declared for Linux and macOS, and both legs run
in the release gate.

### Clone and Install

```bash
git clone https://github.com/automagik-dev/genie.git
cd genie
bun install
```

### Build

Genie bundles to a single file for distribution:

```bash
bun run build
```

This produces `dist/genie.js` (~2 MB minified) with all dependencies inlined. The shebang `#!/usr/bin/env bun` makes it directly executable. No runtime dependencies need to be co-located.

### Run from Source

During development, run directly from source:

```bash
bun run src/genie.ts
```

Or link globally for the `genie` command to point at this checkout. The `bin`
entry resolves to `dist/genie.js`, so build before linking, and rebuild after
every change you want the linked command to pick up:

```bash
bun run build
bun link
```

## Code Style

Genie uses [Biome](https://biomejs.dev/) for formatting and linting.

| Rule | Setting |
|------|---------|
| Quotes | Single quotes |
| Indentation | 2 spaces |
| Line width | 120 characters |
| Trailing commas | Always |
| Commits | Conventional commits (commitlint) |

### No console in `src/**`

Biome's `noConsole` rule is set to `"error"`, so **every** `console.*` call is
banned in source files — not only `console.log`. Use the CLI's own output
functions instead. The rule is relaxed to `"off"` only in the test and script
overrides.

## Quality Gates

Run the full quality gate with:

```bash
bun run check
```

This runs eight steps in sequence, stopping at the first failure:

| Gate | Command | What It Checks |
|------|---------|----------------|
| Type check | `bun run typecheck` | Three `tsc --noEmit` runs: the root, `plugins/dsh-genie-board/tsconfig.json`, and `plugins/dsh-workflow-loader/tsconfig.json` |
| Lint | `bun run lint` | `biome check .` — formatting, code quality |
| Dead code | `bun run dead-code` | `bunx knip` — unused exports, dependencies |
| Skills lint | `bun run skills:lint` | Strict SKILL.md frontmatter, house size, real `genie` commands, retired vocabulary |
| Wishes lint | `bun run wishes:lint` | Every brainstorm link in `.genie/wishes/` resolves to a real file |
| Complexity budget | `bun run lint:complexity-budget` | Drift against the recorded cognitive-complexity ceilings |
| Orca bundle parity | `bun run lint:orca-bundle` | The Orca plugin entrypoint bundle matches its source |
| Tests | `bun test` | All `*.test.ts` files |

`bun run check:fast` runs the same sequence minus `bun test`.

<Note>
`bun run dead-code` (knip) has pre-existing false positives for biome, commitlint, and husky devDeps. These are not regressions.
</Note>

### Running Individual Gates

```bash
bun run typecheck           # Type checking only
bun run lint                # Linting only
bun run dead-code           # Dead code detection only
bun test                    # All tests
bun test src/lib/v5/task-state.test.ts  # Single file
```

## Testing

### Framework

Tests use `bun:test` (import from `'bun:test'`).

### Conventions

| Convention | Detail |
|-----------|--------|
| File pattern | Colocated `*.test.ts` next to source |
| Fixtures | tmpdir with cleanup in `afterEach` |
| Git tests | Real git repos in `/tmp`, not mocks |
| Concurrency | `Promise.allSettled()` pattern |
| Isolation | Set `process.env.GENIE_HOME` to tmpdir |

### Example Test

```typescript
import { afterEach, describe, expect, test } from 'bun:test';
import { mkdtempSync, rmSync } from 'node:fs';
import { join } from 'node:path';
import { tmpdir } from 'node:os';

describe('myModule', () => {
  let tempDir: string;

  afterEach(() => {
    if (tempDir) rmSync(tempDir, { recursive: true, force: true });
  });

  test('does the thing', () => {
    tempDir = mkdtempSync(join(tmpdir(), 'genie-test-'));
    process.env.GENIE_HOME = tempDir;

    // ... test code ...

    expect(result).toBe(expected);
  });
});
```

## Plugin Development

Genie ships **exactly one plugin to end users, and it is the Orca plugin.** There is no Claude Code plugin, no plugin
marketplace registration, no MCP server, no hook definitions, and no editor-specific integration. If you are extending
Genie, you are almost certainly writing a **skill** (below) or a **saved workflow**, not a plugin.

The repository carries three plugin trees, only the first of which is a product deliverable:

| Tree | What it is |
|------|------------|
| `plugins/genie` | The Orca plugin payload — the one plugin Genie ships |
| `plugins/dsh-genie-board` | DSH board plugin, with its own `tsconfig.json` in the typecheck gate |
| `plugins/dsh-workflow-loader` | DSH workflow-loader plugin, with its own `tsconfig.json` in the typecheck gate |

### The Orca plugin payload

`plugins/genie` has no `src/` directory — the manifest and the handlers sit at its root:

```text
plugins/genie/
├── orca-plugin.json          # The Orca manifest — must sit at the install tree's ROOT
├── plugin.json               # Plugin metadata
├── package.json              # Versioned alongside the root package.json
├── orca-entrypoint.ts        # The entrypoint source
├── orca-entrypoint.min.js    # Its bundled form, checked by `bun run lint:orca-bundle`
├── orca-runtime.ts           # Handlers over `orca orchestration … --json`
├── references/               # The public Orca boundary contract
├── README.md
└── *.test.ts                 # Colocated tests
```

Two constraints are load-bearing and enforced by `scripts/orca-manifest-parity.test.ts`:

- **The repository root can never be the install tree.** Orca's loader rejects any tree containing a symlink, and this
  repo has `docs -> .docs-vendor/genie`. It also caps an install at 2000 files / 50 MB, and a dev checkout is roughly
  14,000 files. Do not add a re-rooted `orca-plugin.json` at the repo root.
- **The plugin publishes as a tree-only git ref.** `.github/workflows/orca-plugin-ref.yml` force-pushes a parentless
  commit carrying the `plugins/genie` subtree to `refs/heads/orca-plugin` from `main`, and `orca-plugin-dev` from
  `dev`. Those refs are never merged back.

The only Orca file at the repository root is `orca-marketplace.json`, a source-only, versionless index that no release
tarball contains.

### Adding Skills

Skills are markdown files that define agent behavior. To add a new skill:

1. Create `skills/<skill-name>/SKILL.md`
2. Add frontmatter with `name`, `description`, and optionally `category` and `mutates`
3. Write the skill prompt in the body

`scripts/skills-lint.ts` allows exactly four frontmatter keys — `name`,
`description`, `category`, `mutates` — and fails `bun run check` on any other.
There is no `triggers` key: a skill is selected by its description, not by a
declared trigger list.

```markdown
---
name: my-skill
description: Does something useful
category: authoring
mutates: repo
---

# My Skill

Instructions for the agent when this skill is invoked...
```

Creating the file does not make the skill available to an agent. Skills reach
agents through the skills.sh channel, which runs on install and on
`genie update`, and most agents pick a new skill up only at the next session
start.

## Commit Conventions

Genie uses [conventional commits](https://www.conventionalcommits.org/) enforced by commitlint:

| Prefix | Use |
|--------|-----|
| `feat:` | New features |
| `fix:` | Bug fixes |
| `chore:` | Maintenance |
| `docs:` | Documentation |
| `refactor:` | Code restructuring |
| `test:` | Test additions/fixes |

### Branch Naming

```text
feat/<description>
fix/<description>
chore/<description>
docs/<description>
refactor/<description>
test/<description>
```

### PR Workflow

1. Branch from `dev`
2. Make changes, commit with conventional messages
3. Push and create PR targeting `dev`
4. Human reviews and merges `dev` → `main` when ready

## Known Gotchas

- **File lock timeout force-removes are intentional** — prevents deadlocks from crashed processes. The `open('wx')` after unlink is atomic, so only one process wins.
- **`bun link` runs the build output, not your sources** — a source edit is invisible to the linked `genie` until you re-run `bun run build`.
- **A version bump touches three files** — `package.json`, `plugins/genie/orca-plugin.json`, and `plugins/genie/package.json`, the `JSON_FILES` list in `.github/workflows/version.yml`. The scheme is `<major>.YYMMDD.N`: a major bump moves the leading number only, leaving the CalVer date and the same-day counter untouched.
- **Commit messages are gated locally** — commitlint runs from `.husky/commit-msg`, so a non-conventional message is rejected before it reaches CI.
