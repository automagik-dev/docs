A **wish** is Genie's unit of work. It is a structured document (`WISH.md`) that defines what to build, how to validate
it, and how to break it into parallelizable execution groups. It lives in git, so you review it like code.

## The Lifecycle

Every wish flows through the same lifecycle, with a review gate between each pair of stages:

```text
brainstorm → design review → wish → plan review → work → implementation review
```

| Stage | Skill | Input | Output |
|-------|-------|-------|--------|
| Explore | `/brainstorm` | Rough idea | `DESIGN.md`, independently reviewed |
| Deliver one task | `/wish` | One decided objective | A merge-ready PR, or a refusal naming the route it needs |
| Plan | `/wish` (plan entry) | Design document | `WISH.md` with criteria and groups |
| Execute | `/work` | Approved `WISH.md` | Code changes, tests, docs |
| Validate | `/review` | Completed work | SHIP, FIX-FIRST, or BLOCKED |
| Ship | orchestrator | SHIP verdict | Pull request for you to merge |

<Note>
  Not every objective needs a plan. For **one decided task**, [`/wish`](/genie/skills/wish) skips `WISH.md` entirely:
  it admits the task, works it in its own worktree, runs the gate, hands the commit to an independent reviewer, and
  opens a merge-ready PR. A `WISH.md` is what you write when the work is bigger than one task.
</Note>

## Anatomy of a WISH.md

Every wish contains these sections:

### Header

```markdown
# Wish: Add Dark Mode Toggle

| Field | Value |
|-------|-------|
| **Status** | APPROVED |
| **Slug** | `dark-mode-toggle` |
| **Date** | 2026-03-24 |
```

The **status** tracks the wish lifecycle. These six are the durable vocabulary — SessionStart, resume routing, and the
loop skills all read them:

| Status | Meaning |
|--------|---------|
| `DRAFT` | Being written, not yet approved |
| `FIX-FIRST` | Review found bounded gaps that block acceptance |
| `APPROVED` | Ready for execution |
| `IN_PROGRESS` | Currently being worked on |
| `BLOCKED` | Cannot proceed — needs a decision |
| `SHIPPED` | Reviewed, merged, done |

<Warning>
  A reviewer's chat verdict is **evidence, not state**. SHIP, FIX-FIRST, and BLOCKED are what a review returns; the
  statuses above are what the wish carries. The **orchestrator** appends the review evidence to `WISH.md` and updates
  the status — no verdict advances a wish on its own.
</Warning>

### Scope

Defines clear boundaries — what's **in** and what's **out**:

```markdown
## Scope

### IN
- Dark mode CSS variables
- Toggle component in settings
- Persistent preference in localStorage

### OUT
- System theme detection (future wish)
- Dark mode for marketing pages
```

### Success Criteria

Checkboxes that define "done". These are what `/review` validates against:

```markdown
## Success Criteria

- [ ] Toggle renders in settings page
- [ ] CSS variables switch between light/dark
- [ ] Preference persists across sessions
- [ ] No FOUC on page load
- [ ] All existing tests pass
```

### Execution Groups

Parallelizable work units. Each group names the role that executes it:

```markdown
## Execution Groups

### Group 1: CSS Variables
**Agent:** engineer
**Deliverables:**
1. Define CSS custom properties for both themes
2. Update existing component styles to use variables

### Group 2: Toggle Component
**Agent:** engineer
**Deliverables:**
1. Build toggle component
2. Wire to localStorage
**depends-on:** Group 1
```

Groups with `depends-on` run in order. Independent groups run in parallel — this is how Genie achieves speed.

## Wish State

Genie tracks execution state in the per-repo SQLite database, `<repo>/.genie/genie.db`. Each execution group becomes a
card carrying the wish slug, with dependency edges between cards; the ready set is whatever has no unmet dependency.
There is no server and no daemon — a command opens the file, runs one transaction, and exits.

The card state records:

- Which groups are complete and which are ready
- Which roster agent is declared on each card
- The card's lane and its stage log — handoff reports and gate pointers
- Timestamps, claims, and heartbeat liveness

<Note>
  `tasks.wish` is a **lifecycle slug**, not proof that a `WISH.md` exists. A card carries the same stable slug from the
  moment `.genie/brainstorms/<slug>/` is created, threading Idea → Brainstorm → Wish → Work → Review → Done. The slug
  is identity; the documents catch up with it.
</Note>

### Shared across worktrees

All linked worktrees of one repository share the same `genie.db`, resolved via `git rev-parse --git-common-dir`. A card
created in one worktree is instantly visible in another — there is no sync step between worktrees, and no per-worktree
copy to reconcile.

### The canonical snapshot

`<repo>/.genie/roadmap.json` is the **canonical** board snapshot and is tracked in git; `genie.db` itself is gitignored
and materializes from it. `genie task sync` three-way reconciles the two, and the git hooks run it on pull, merge,
rewrite, and pre-commit — so the board travels with the branch instead of living on one machine.

## File Locations

| Location | Path | Tracked in git |
|----------|------|----------------|
| Wish document | `.genie/wishes/<slug>/WISH.md` | Yes |
| Design document | `.genie/brainstorms/<slug>/DESIGN.md` | Yes |
| Index | `.genie/INDEX.md` | Yes |
| Board snapshot | `.genie/roadmap.json` | Yes — the canonical roadmap |
| Execution state | `.genie/genie.db` | No — SQLite, materialized from `roadmap.json` |

Brainstorm notes other than `DESIGN.md` are machine-local and gitignored: the reviewed design is the artifact that
travels, not the scratch work behind it.

## CLI Commands

Wish work shows up as cards in the database — see the [Task CLI reference](/genie/cli/tasks) for the full subcommand
list.

```bash
genie board --wish <slug>            # the cards for one wish, rendered live
genie task status <id>               # one card: detail, dependencies, stage log
genie context --wish <slug> --plan   # preview the spawn context, read-only
genie wish lint                      # lint .genie/wishes for structure
```

`genie context --wish <slug> [--group <g>]` emits one line of versioned JSON — the composed branch, the resolved base
SHA, and the ready tasks — which is what a spawn consumes to set up an isolated worktree. `--plan` previews it without
writing anything.

`genie wish lint [--dir <repo>]` checks a repository's `.genie/wishes` for structural problems and writes nothing:
exit `0` clean, `1` findings, `2` when the root is refused.

## Best Practices

<AccordionGroup>
  <Accordion title="Keep wishes small">
    A wish should be completable in one session. If it has more than 6 execution groups, consider splitting it into
    multiple wishes — or, if it collapses to a single decided task, skip the plan and use `/wish` directly.
  </Accordion>
  <Accordion title="Write testable criteria">
    Each success criterion should be verifiable by a command or assertion. Avoid subjective criteria like "code is clean."
  </Accordion>
  <Accordion title="Declare dependencies explicitly">
    If Group 3 needs Group 1's output, say `depends-on: Group 1`. Genie turns that into a dependency edge and uses it
    to compute the ready set.
  </Accordion>
  <Accordion title="Scope aggressively">
    The OUT section is as important as IN. Explicitly listing what you won't do prevents scope creep.
  </Accordion>
  <Accordion title="Let the orchestrator own the status">
    Don't hand-edit a wish's status to match a verdict you read in chat. The orchestrator writes the evidence and the
    status together, which is what keeps `WISH.md` and the board telling the same story.
  </Accordion>
</AccordionGroup>
