A **skill** is a structured prompt file that encodes a workflow. When you invoke `/brainstorm` or `/work`, you are
loading a skill — a Markdown document with YAML frontmatter that gets read into the agent's context.

Skills are not code. They are prompt programs: they define phases, decision points, output formats, and validation
steps that the agent follows.

## How Skills Reach Your Agent

Genie delivers its skills through the [skills.sh](https://skills.sh) channel, into **each agent's own global skill
home** — `~/.claude/skills`, the shared `~/.agents/skills` that Codex and others read, and so on. Delivery happens at
two moments and only two:

| When | What happens |
|------|--------------|
| `genie install` (the post-install finisher) | The skills that shipped inside that release are installed to every agent Genie detects |
| `genie update` | The binary is replaced, then the skills are reinstalled from that release's own tree |

<Warning>
  Skills do **not** appear instantly, and Genie never delivers one by dropping a file into your repository. If a skill
  is missing, run `genie update` — it owns every mutation on this surface. `genie doctor` only observes it. Most agents
  also pick up new skills on the *next* session start, so restart your session before assuming the install failed.
</Warning>

## Runtime Neutrality

Genie's skills are written to be runtime-neutral. They name **portable roles** — an orchestrator, an engineer, an
independent reviewer — and let each runtime map those roles onto its own native subagents. Genie installs **no agent
profiles and no hooks**; it does not need to know how your agent spawns work.

What changes per runtime is only how you invoke a skill:

| Runtime | Invocation |
|---------|------------|
| Claude Code | A slash command: `/wish`, `/work`, `/review` |
| Everything else | By name, or in plain language: "use the wish skill to …" |

## Skill Anatomy

Every skill lives in `skills/<name>/SKILL.md`, and its frontmatter allows **exactly four keys**:

```yaml
---
name: brainstorm
description: Explore an ambiguous idea with the user, settle scope and success criteria, and produce an independently reviewed design for wish.
category: lifecycle
mutates: true
---

# Brainstorm

## Phase 1: Understand the idea
...
```

| Field | Purpose |
|-------|---------|
| `name` | Skill identifier — matches how the skill is invoked |
| `description` | One-line summary, used for routing and shown in skill listings |
| `category` | Groups the skill in the catalogue |
| `mutates` | Whether the skill is allowed to change the repository |

<Note>
  There is **no `triggers:` key**. A skill is selected by its `description` and by you asking for it — nothing else in
  the frontmatter routes it.
</Note>

### Lifecycle

## Invoking Skills

Pass whatever context you have as the argument:

```text
/brainstorm Add a webhook system for real-time notifications
```

Skills also call each other, which is how the loop holds together without you driving every hop:

- `/wish` routes back to `/brainstorm` when the objective is not decided yet
- `/work` hands finished work to `/review`
- `/review` returning FIX-FIRST routes to `/fix`, which re-reviews when it is done
- `/dream` runs `/work` → `/review` loops across a batch of SHIP-ready wishes

<Warning>
  The reviewer is never the engineer. `/review` runs as a **different subagent** from the one that wrote the code, and
  its verdict is evidence, not state: the orchestrator is what persists the review into `WISH.md` and advances the
  work.
</Warning>

## Writing Your Own Skill

1. Create `skills/<name>/SKILL.md`
2. Add frontmatter with `name`, `description`, `category`, and `mutates` — those four keys and no others
3. Write the instructions in Markdown: phases, decision points, the exact shape of the output
4. Install it into your agent's skill home the same way you install any skills.sh skill

```yaml
---
name: deploy
description: Guide a deployment to staging and production, with a pre-flight gate before each promotion.
category: ops
mutates: true
---

# Deploy

## Phase 1: Pre-flight checks
- Verify the full gate passes
- Check CI status on the target branch
- Confirm the target environment

## Phase 2: Promote
...
```

<Tip>
  The `authoring` skill exists for exactly this: it writes and revises skills against the shipped contract, so your
  skill reads like the ones Genie delivers. `skill-audit` then tells you whether it overlaps something that already
  exists.
</Tip>

## Skills and the CLI

Skills carry the judgement; the CLI carries the state. A skill decides what to do next and writes the documents; the
[16 top-level commands](/genie/cli/infrastructure) open `.genie/genie.db`, run one transaction, and exit. Neither one
runs a daemon.

| | Skill | CLI command |
|---|-------|-------------|
| **What** | A prompt program your agent reads | A process that opens the database and exits |
| **Lives in** | Your agent's global skill home | `~/.local/bin/genie` |
| **State** | Stateless — the conversation is the context | Per-repo SQLite plus git-tracked documents |
| **Invocation** | `/wish`, or by name | `genie board`, `genie task status <id>` |
