# Board Commands

A Genie board is a **name and an ordered list of lanes**. That is the whole object. The Kanban view you get from
`genie board` is **derived by query** every time you run it: there is no stored view state, no cached layout, no
per-repo "active board" setting, and nothing to reconcile when a card moves.

That is the design choice this page is really about. A board that stores a rendering has two sources of truth for
where a card is — the card and the view — and they drift. Deriving the view on every invocation means the cards are
the only answer.

<Note>
  This page describes **standalone** mode, the default. Under explicitly selected Orca authority
  (`genie setup --orchestration-mode orca`), `genie board` and `genie idea` exit **2** with one fixed line naming the
  remedy `genie setup --orchestration-mode standalone`. Orca owns the lifecycle in that mode; Genie keeps no shadow
  copy.
</Note>

## `genie board`

Render the board view.

```bash
genie board [--board <ref>] [--wish <slug>] [--json]
```

| Flag | Description |
|------|-------------|
| `--board <ref>` | Scope to a board id or name |
| `--wish <slug>` | Scope to a wish slug |
| `--json` | Output as JSON |

The two scopes do different jobs. `--board` picks the board whose lanes the cards are rendered **into**; `--wish`
narrows the card set to one wish slug. They compose, and either can be used alone.

Only `--board` produces the lane view, because only a board defines lanes:

```bash Terminal
$ genie board --board <ref>
Board — board "<name>"
════════════════════════════════════════════════════════
  Idea: 0   Brainstorm: 0   Wish: 1   Work: 2   Review: 0   Done: 1

── Idea (0 cards) ──
  (empty)

── Wish (1 card) ──
  t_…  <card title>
```

With no `--board` — including `genie board --wish <slug>` on its own — the read is **laneless**: with no board to
supply lane names, the cards are grouped into three status columns instead, `Ready`, `In Progress` and `Done`. A
blocked card rides in `Ready` with a badge; blocked is a state of a card, not a place to put it.

```bash Terminal
$ genie board --wish <slug>
Board — wish "<slug>"
════════════════════════════════════════════════════════
  Ready: 2   In Progress: 1   Done: 1
```

Every render names its own scope on the first line — `all tasks` unscoped, `board "<name>"`, `wish "<slug>"`, or both
when the flags compose — so a screenshot of a board read always says what it was a read of.

A board whose stored lane metadata is unusable renders the same laneless way, with one explicit note saying so. It is
not a read failure: an unreadable lane list is a reason to show you the cards plainly, not a reason to show you
nothing.

<Warning>
  An empty scope is **refused**, never widened. `genie board --board ""` and `genie board --wish ""` — what an unset
  shell variable expands to — fail rather than silently reading every task in the repository.
</Warning>

<Tip>
  `--json` is the scripting surface. Because the view is derived, the JSON is a snapshot of the query result, not of a
  stored document — run it again after a `genie task move` and it reflects the move with no refresh step. Very large
  reads are capped against a response budget: the answer narrows each card's embedded history and says so, or refuses
  and tells you to scope by `--wish`.
</Tip>

## `genie board create`

```bash
genie board create <name> [--lanes <lanes>]
```

| Flag | Description |
|------|-------------|
| `--lanes <lanes>` | Comma-separated lane names, overriding the lifecycle default |

With no `--lanes`, a new board gets the six lifecycle lanes:

```text
Idea → Brainstorm → Wish → Work → Review → Done
```

Those lanes mirror the path a piece of work actually takes through Genie, and a card's wish slug stays constant across
all six — the lane is progress, the slug is identity.

Lanes are names. There are **no column gates and no board templates**: a lane does not decide who may move a card out
of it, and moving a card never triggers anything. A lane carried in from a snapshot may hold a display-only action
hint, printed on the lane header — nothing executes it. Sequencing is the orchestrator's job, and the enforcement that
does exist lives on the card: `genie task block` refuses a checkout, `genie task done` recomputes the ready set.

## `genie board list`

```bash
genie board list [--json]
```

Lists the boards in this repository with their lane and card counts.

## `genie idea`

```bash
genie idea <text...>
```

Capture an idea into the roadmap board's **Idea** lane. If the roadmap board does not exist yet, `genie idea` creates
it with the six lifecycle lanes and drops the card in — so the first idea in a fresh repository needs no setup step
before it.

This is the deliberately low-friction entry point: one verb, free text, no flags to decide. Everything else about the
card — a wish slug, an assignment, a lane other than Idea — is added later with [`genie task`](/genie/cli/tasks) once
the idea has earned it.

## Where board state lives

Boards and cards share one database: `<repo>/.genie/genie.db`, SQLite via `bun:sqlite`, in WAL mode, with no daemon.
Every linked worktree resolves the same file through `git rev-parse --git-common-dir`, so a board created in one
worktree is visible in all of them immediately.

The git-tracked, canonical form is `.genie/roadmap.json`, which `genie task export --write` publishes and
`genie task sync` reconciles on pull, merge, rewrite and pre-commit. Boards travel with the repository that way, as a
reviewable diff — not as a database file anyone has to copy.
