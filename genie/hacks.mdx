## Planning & scope

### Hack 1: Let one task skip the plan

**Problem:** You write a `WISH.md` with one execution group, review the plan, then dispatch one agent. Three gates for a change that was obvious from the first sentence.

**Solution:** `/wish` already knows the difference. Hand it **one decided task** and it skips the plan entirely: it admits the task, builds it in its own worktree, runs the gate, has a *different* agent review the commit, and opens a merge-ready PR. Only work that is genuinely bigger than one task becomes a `WISH.md`.

```text
/wish rename the --lane flag to --to across task move and its tests
```

**Benefit:** One decided change ships in one pass instead of four, and the plan artifact stops being a formality nobody reads.

**When to use:** Whenever you could describe the whole change and its acceptance in a sentence. If you find yourself writing "and also", it is a wish, not a task.

---

### Hack 2: Lint the wish before anything acts on it

**Problem:** An agent works for twenty minutes against a wish whose group has no acceptance criteria, and the review has nothing to check against.

**Solution:** `genie wish lint` checks a repository's `.genie/wishes` for structure. It writes nothing and its exit code is the whole contract: **0** clean, **1** findings, **2** the root was refused. That drops straight into a pre-commit hook or a CI step — treat 2 as a failure, because a `--dir` you typed that does not resolve is refused rather than reported clean.

```bash
genie wish lint                 # this repository
genie wish lint --dir ../other  # any other checkout
```

**Benefit:** A malformed plan fails in a second instead of after a wasted execution wave.

**When to use:** Always, in CI. Also worth running by hand right after `/wish` writes a large plan, before you approve it.

## Parallel work

### Hack 3: Shape groups for waves, not for tidiness

**Problem:** A wish with six groups runs almost sequentially because every group quietly depends on the one before it.

**Solution:** Dependencies are what decide the wave, so write `depends-on` deliberately and keep independent work independent. `/work` dispatches each wave through your agent's own native subagents; groups with no shared dependency run together.

```text
Wave 1 (parallel): Group 1, Group 2, Group 3   depends-on: Group 0
Wave 2 (parallel): Group 4, Group 5            depends-on: Group 1
Wave 3:            Group 6                     depends-on: all
```

```bash
genie board                 # the live kanban, derived by query
genie task status <id>      # one card: dependencies, stage log, assignment
```

**Benefit:** A six-group wish that ran in sequence finishes in roughly the time of its longest chain. The bottleneck moves from execution to review, which is where you want it.

**When to use:** Any wish with three or more groups where at least two touch different files.

---

### Hack 4: One database, every worktree

**Problem:** You cut a worktree for a group, create a task in it, and then cannot see that task from the main checkout.

**Solution:** You can — that is already how it works. Every linked worktree resolves the same `.genie/genie.db` through the git **common** directory, so there is no sync step and nothing to reconcile. Only the canonical board snapshot (`.genie/roadmap.json`) is a file in git, and `genie task sync` reconciles it three ways on merge, rewrite, and pre-commit.

```bash
git worktree add ../feature-x -b wish/feature-x origin/dev
(cd ../feature-x && genie task list)   # same cards, same database
```

**Benefit:** Worktree isolation for the *files* without fragmenting the *state*.

**When to use:** Every time you fan work out. Do not copy `genie.db` between worktrees — you will create two histories that `task sync` then has to merge.

## Skills & automation

### Hack 5: Write a custom skill for anything you've explained twice

**Problem:** You keep typing the same sequence for a recurring task — migrations, seed data, restart. It is error-prone and tedious to explain each time.

**Solution:** A skill is just Markdown with YAML frontmatter. Drop a file in `skills/<name>/SKILL.md` and it becomes a slash command in Claude Code, and a name your other agents can invoke, instantly. No code, no registration, no build step.

```bash
mkdir -p skills/reset-dev
cat > skills/reset-dev/SKILL.md << 'EOF'
---
name: reset-dev
description: Reset dev environment — migrate, seed, restart
---

# Reset Dev Environment

Run these steps in order:

1. **Stop services:** `docker compose down`
2. **Reset database:** `docker compose run --rm api rails db:reset`
3. **Run migrations:** `docker compose run --rm api rails db:migrate`
4. **Seed data:** `docker compose run --rm api rails db:seed`
5. **Start services:** `docker compose up -d`
6. **Verify:** `curl -s http://localhost:3000/health | jq .status`

Report the health check result when done.
EOF
```

**Benefit:** Your team's tribal knowledge becomes reusable and version-controlled. New team members — human or agent — get the same consistency.

**When to use:** Any workflow you have explained more than twice. Keep the prose runtime-neutral: name a role, not a product, so the skill works in every agent that reads it.

### Hack 6: Teach a microagent your repository's own taste

**Problem:** A general model keeps missing the conventions that are obvious to everyone on your team, and you cannot tell whether a prompt change actually helped.

**Solution:** `genie mikro` is a small runtime for repository-local microagents — a prompt plus an answer schema, returning validated JSON whose every citation is checked against the tree. It can **measure** itself.

```bash
genie mikro init                                     # seed the default agents into this repo
genie mikro fixtures --from-commits HEAD~50..HEAD \
                     --agent wish-context             # a fixture set from your own history
genie mikro bench wish-context                        # score it mechanically
genie mikro coach wish-context                        # propose, patch a copy, bench before/after
```

Agents resolve repo-first: `--agents-dir`, then this checkout's `.mikro/agents/<agent>/agent.yaml`, then the release's templates. The answer names which source won, so you always know what ran.

**Benefit:** A prompt change stops being a vibe. You get a before-and-after number over fixtures drawn from your own commits.

**When to use:** Any narrow, repeated judgement — triaging an issue, extracting wish context, prepping a review — where you would otherwise re-explain the same conventions in every prompt.

## Operations

### Hack 7: Read doctor's JSON, not its prose

**Problem:** `genie doctor` prints one aggregated line per check, which is exactly right for a human and useless for a script.

**Solution:** `--json` carries the full entry list behind a summarized line while the human output stays readable. Mode drift is the case that matters: the human line names at most five entries, and `checks[].modeDrift.entries` carries every one of them.

```bash
genie doctor --json | jq '.checks[] | select(.status == "warn") | .name'
genie doctor --json | jq '[.checks[].modeDrift.entries // empty] | flatten | length'
```

**Benefit:** You get the full list without a thousand lines of terminal, and the same command works in CI.

**When to use:** Any time you want to act on doctor's output rather than read it. Remember doctor is a **read-only observer** of the skills channel — not even `--fix` repairs it. `genie update` owns every mutation there.

---

### Hack 8: Tighten a budget in config, never in prose

**Problem:** You want the repair loop to give up sooner on this machine, and you do not want to argue with a skill about it.

**Solution:** Budgets live in `~/.genie/config.json`, and the skills read them through the CLI rather than restating a number. Configuration may only **tighten** a gate: every key has a schema ceiling, and a value past it fails the parse so the default stands.

```bash
genie config get budgets.maxEscalationsPerGroup
genie config get budgets.maxFableCallsPerWish --json
```

**Benefit:** One place to change, no drift between what the config says and what a skill believes.

**When to use:** When a repair loop is burning budget on work that should have gone back to review. Lower the number; you cannot raise it past the reviewed ceiling, and that is the point.

## Contributing

Have a hack that's not here? We want it. The best docs come from people who actually hit the problem.

### Format

Every hack follows this structure — keep it concrete, skip the theory:

```markdown
### Hack N: Your Hack Title

**Problem:** What situation does this solve? (1-2 sentences)

**Solution:** How does it work? (Brief explanation)

\`\`\`bash
# Concrete commands or code
\`\`\`

**Benefit:** What do you gain? (Quantify if possible)

**When to use:** In what situations should someone reach for this?
```

### Submit via PR

The fastest way to contribute:

```bash
# 1. Fork the docs repo
gh repo fork automagik-dev/docs --clone

# 2. Add your hack to genie/hacks.mdx
#    Follow the format above — problem → solution → code → benefit → when

# 3. Create a PR
git add genie/hacks.mdx
git commit -m "hack: your hack title"
gh pr create --base dev --title "hack: your hack title" --body "
## New Hack

**Category:** planning | parallel | skills | ops
**Problem:** Brief description
**Tested on:** Genie version, OS, agent
"
```

Or use `/genie-hacks contribute` for guided PR creation.
