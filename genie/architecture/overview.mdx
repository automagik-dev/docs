# Architecture Overview

Genie is a planning-and-execution layer for AI coding agents. It turns a described intent into a reviewed pull request,
and it does that with **no resident process of any kind**.

<Note>
  The v4 harness — an embedded PostgreSQL backend, pane-based process orchestration, executor registries, a NATS event
  spine, the full-screen console, and the desktop app — is gone. What remains is the part that always did the work: the
  skills, the documents, and one SQLite file of state. v4 is preserved on the
  [`v4` branch](https://github.com/automagik-dev/genie/tree/v4) for anyone still running it.
</Note>

## The three surfaces

Genie ships exactly three things, and nothing else:

| Surface | Delivered by | Recorded at |
|---------|--------------|-------------|
| **The signed binary** | `install.sh`, then `genie update` | `~/.genie` |
| **The skills** | The pinned [skills.sh](https://skills.sh) CLI, run over the tree the signed release put on disk | `~/.genie/skills-install.json` |
| **The Orca plugin** | An optional lifecycle integration you register with Orca yourself | Orca's own install record |

There is no Claude marketplace plugin, no Codex plugin, no Genie-installed hooks, no MCP server, and no role-agent
profiles. Nothing Genie installs runs inside your agent's event loop.

## Lifecycle authority

Genie has two explicit modes, and the mode is always a deliberate selection — never inferred from what is installed.

<CardGroup cols={2}>
  <Card title="standalone (default)" icon="hard-drive">
    Genie owns the per-repo `genie.db` and the roadmap snapshot. This is the default, including when the config omits
    `orchestration.mode`.
  </Card>
  <Card title="orca" icon="plug">
    Orca is the sole lifecycle authority, reached through the closed public `orca orchestration … --json` boundary.
    Genie opens no local lifecycle database and keeps **no fallback**: if Orca is unavailable, the operation fails.
  </Card>
</CardGroup>

In Orca mode the CLI is explicit about what it will not do. `genie task`, `genie board` and `genie idea` exit **2** with
one fixed line naming the remedy — that closed list of three root verbs is the whole list. `genie task sync` exits 0 and
prints nothing, so the git hooks that call it on every commit stay silent. `genie context --wish <slug> --plan` still
answers, read-only, because it is the one question an agent needs answered to cut a worktree.

Switching either way is `genie setup --orchestration-mode <mode>`, and neither direction imports the other's state.

## Data flow: intent to PR

<Steps>
  <Step title="Brainstorm">
    `/brainstorm` explores the idea until it is concrete, and writes a `DESIGN.md` under `.genie/brainstorms/<slug>/`.
    The design gets an independent review before anything is planned.
  </Step>
  <Step title="Wish">
    `/wish` admits the work. **One decided task** is delivered end to end — its own worktree, the gate, an independent
    reviewer, a merge-ready PR — with no plan at all. Work that is bigger than one task becomes a `WISH.md` with scope,
    acceptance criteria, and parallelizable execution groups.
  </Step>
  <Step title="Work">
    `/work` fans agents out through the active client's **native subagents**, wave by wave in dependency order. Each one
    claims a task; state changes serialize through `genie.db` rather than through a coordinator. Worktree isolation,
    where required, is arranged by the orchestrator.
  </Step>
  <Step title="Review">
    Review runs as a different subagent from the one that wrote the code — reviewer ≠ engineer — so the verdict is
    independent evidence against the wish criteria. It returns SHIP, FIX-FIRST, or BLOCKED.
  </Step>
  <Step title="Persist and ship">
    A reviewer verdict is evidence, not state. The **orchestrator** appends the review evidence, updates `WISH.md`, and
    is the only actor that runs `genie task done`. Then the PR is opened for a human to merge.
  </Step>
</Steps>

## State, and where it lives

| Scope | Location | What lives here |
|-------|----------|-----------------|
| Global | `~/.genie/` (relocated by `GENIE_HOME`) | `config.json`, the skills install record, state backups, worktrees |
| Per-repo, in git | `<repo>/.genie/{wishes,brainstorms/*/DESIGN.md,INDEX.md,roadmap.json}` | Every document a human reviews |
| Per-repo, operational | `<repo>/.genie/genie.db` | Tasks, dependency edges, lanes, stage log |

All linked worktrees of a repository share one `genie.db`, resolved from the git common directory, so a task created in
one worktree is immediately visible in another with no sync step. Documents live in git; operational state lives in
SQLite. That split is the contract.

## Microagents

`genie mikro` is a small, separate runtime for **repository-local microagents** — narrow agents defined by a prompt and
an answer schema, which return validated JSON whose every citation is verified against the tree under review.

```bash
genie mikro init                       # seed this release's default agents into a repository
genie mikro call <agent> --prompt '…'  # run one agent, get validated JSON back
genie mikro fixtures --from-commits    # build a fixture set from the repo's own history
genie mikro bench <agent>              # score the agent mechanically over its fixtures
genie mikro coach <agent>              # propose, patch a copy, bench before and after
```

Agents resolve **repo-first**: the `--agents-dir` flag wins, then the invoking checkout's
`.mikro/agents/<agent>/agent.yaml`, then the release's own templates. The trusted root is the invoking checkout, never
the tree being reviewed — and the answer names which source won.

## Environment variables

| Variable | Effect |
|----------|--------|
| `GENIE_HOME` | Relocates all global state from `~/.genie` |
| `GENIE_AGENT_NAME` | Worker identity for task claims and stage-log entries |
| `GENIE_AGENT_ID` | Fallback worker identity; both floor at `cli` |
| `GENIE_TEAM` | Default team when `--team` is not provided |
| `GENIE_WORKTREES_DIR` | Override the worktrees base doctor and review snapshots read |
| `GENIE_CONFIG_FILE` | Override the resolved config path |
