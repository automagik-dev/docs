# /work — Execute Wish Plan

Orchestrate execution of an approved wish. The orchestrator never executes directly — always dispatches via subagent.

## When to Use

- An approved wish exists and is ready for execution
- After `/review` returns SHIP on the plan
- Orchestrator needs to dispatch implementation tasks to subagents

## Flow

1. **Load wish** — read `.genie/wishes/<slug>/WISH.md`, confirm scope.
2. **Pick next task** — select next unblocked pending execution group.
3. **Self-refine** — dispatch `/refine` on the task prompt with WISH.md as context.
4. **Dispatch agent** — send the task to a fresh subagent session.
5. **Local review** — run `/review` per group against acceptance criteria. On FIX-FIRST, dispatch fix subagent (max 2 loops).
6. **Quality review** — dispatch review subagent for quality pass (security, maintainability, perf).
7. **Validate** — run the group validation command, record evidence.
8. **Hand back** — the worker posts exactly one `genie task report` on the card.
9. **Repeat** until all groups done.
10. **Handoff** — `All work tasks complete. Run /review.`

## Dispatch

All dispatch goes through the runtime's own subagent surface. Genie starts no
processes and opens no panes of its own:

| Need | Method |
|------|--------|
| Implementation task | One worker subagent per independent execution group |
| Review task | A different subagent running `/review` — never the one that wrote the code |
| Fix task | A fixer subagent running `/fix`, separate from the reviewer |
| Quick validation | `Bash` tool directly — no subagent needed |

## State Management

- **Workers hand back** on the card: one `genie task report <id> --worker <name> -- '<outcome>; <validation> → <result>'` per claim.
- **The coordinator tracks** state with `genie task list --wish <slug>` or `genie board --wish <slug>`, and completes a group with `genie task done <id>`.
- Workers do NOT call `genie task done` — that is the coordinator's responsibility.
- A stale claim is reclaimed by posting `reclaim: from <previous>, idle <duration> — <reason>` as a comment before the new `genie task checkout`.

## Escalation

When a subagent fails or fix loop limit (2) is exceeded:

- Mark task **BLOCKED** in wish
- Create follow-up task with concrete gaps
- Continue with next unblocked task
- Include blocked items in final handoff

## Task Lifecycle Integration

Task state lives in the per-repo SQLite database `.genie/genie.db`. When a card
exists for the work, `/work` drives it at each step:

| Event | Command |
|-------|---------|
| Record the dispatch | `genie task comment <id> --worker orchestrator -- 'dispatch: <role> — <wave>/<group>'` |
| Claim the card before mutating | `genie task checkout <id> --worker <name>` |
| Move the card to another lane | `genie task move <id> --to review` |
| Hand the group back | `genie task report <id> --worker <name> -- '<outcome>; <validation> → <result>'` |
| Relay the review verdict | `genie task comment <id> --worker orchestrator -- 'review: SHIP — validation: <command> → pass'` |
| Complete the group | `genie task done <id>` |

Task integration is graceful — with no card, the flow proceeds from WISH.md
alone. Under `orchestration.mode = orca` the local writes are refused by design
and the same moments are posted through the Orca surface.

## Rules

- Never execute directly — always dispatch subagents
- Never expand scope during execution
- Never skip validation commands
- Never overwrite WISH.md from agents
- Keep work auditable: capture commands + outcomes
- Run local `/review` per group before signaling done
