# /wish — One Task Delivered

Give `/wish` a decided, bounded objective and it comes back with a merge-ready pull request against your integration branch — or with a refusal that names the route the request needs instead. When the work is bigger than one task, the same skill writes the plan at `.genie/wishes/<slug>/WISH.md` for `/work` to execute.

<Note>
  `/wish` used to mean "write a plan". It now means "deliver one task", and the planning path lives on as its plan entry. `/quick` is retired; `/wish` replaces it.
</Note>

## When to Use

- One decided change that should become a green PR in a single pass
- A multi-group effort that needs a durable plan first (the plan entry below)
- Prior `/brainstorm` output that is settled enough to build

Not for work whose cause is unknown (`/report` first) or whose product decision is still open (`/brainstorm` first). `/wish` refuses both, by name.

## Delivering one task

| Stage | What happens |
|-------|--------------|
| **Admit** | A read-only scout reads the repository and estimates the change; a blind judge that never sees the code decides the route and writes the contract — core outcome, declared file set, acceptance criteria — before any code exists |
| **Work** | One executor works in its own worktree on `wish/<slug>`, edits only the declared files, and makes one conventional commit |
| **Gate** | The repository's full check runs once; a push never happens over dead git hooks |
| **Review** | A different, read-only agent scores the exact commit against the criteria written at admission, and blocks if the diff leaves the declared file set |
| **Repair** | Bounded repair rounds, each re-gated and re-reviewed |
| **Publish** | One agent pushes the branch, opens the PR, and reads the remote back — base, head, file set and checks |

Merging is never part of it. `/wish` reports `merge-ready`; you merge.

### Admission band

The scout's estimate is measured against the size band from the wish-duration study: **maximum 25 files, 2,000 insertions, 3 independently reviewable units** (ideal: 10, 800, 2). Anything larger, anything touching a trust-boundary path (CI workflows, git hooks, settings, release scripts, permission surfaces), an open product decision, or an unknown cause comes back **refused**, with the route it needs — `plan`, `brainstorm` or `report` — and nothing created.

### What a run returns

| State | Meaning |
|-------|---------|
| `merge-ready` | Checks pass, the remote matches the local head, the PR's base, head and file set match the contract, and the verdict is SHIP |
| `pr-open` | The PR exists, but its checks had not concluded — re-read them before acting |
| `refused` | Admission chose another route; nothing was created |
| `blocked` | A worktree, hook, denylist or read-back mismatch stopped the run; the reason names which |
| `missed` | The repair budget ran out, or a stage returned nothing; the branch, commit, worktree and any PR are preserved and named |

A rerun with the same objective adopts the worktree it left behind when that worktree is clean and nothing has diverged from the remote. `/wish` never deletes a worktree or a branch — after you merge, `git worktree remove <path> && git branch -d wish/<slug>`.

## Plan a multi-group wish

The direct entry for work bigger than one task: no admission, just the plan. Write `.genie/wishes/<slug>/WISH.md`, then `/review` it, then `/work` executes the approved groups.

### Wish Document Sections

| Section | Required | Notes |
|---------|----------|-------|
| Status / Slug / Date | Yes | Status: DRAFT on creation |
| Summary | Yes | 2–3 sentences: what and why |
| Scope IN / OUT | Yes | OUT cannot be empty |
| Decisions | Yes | Key choices with rationale |
| Success Criteria | Yes | Checkboxes, each testable |
| Execution Strategy | Yes | Wave-based parallel/sequential plan |
| Execution Groups | Yes | Goal, deliverables, acceptance criteria, validation |
| Dependencies | No | `depends-on` / `blocks` using slug |
| QA Criteria | No | Post-merge verification |
| Assumptions / Risks | No | Flag what could invalidate the plan |

### Execution Strategy

Every wish defines waves — this forces the planner to think about ordering, parallelism, and dependencies upfront:

```markdown
### Wave 1 (parallel)
| Group | Agent | Description |
|-------|-------|-------------|
| 1 | engineer | Task A |
| 2 | engineer | Task B |

### Wave 2 (after Wave 1)
| Group | Agent | Description |
|-------|-------|-------------|
| 3 | engineer | Task C |
| review | reviewer | Review Groups 1+2 |
```

Size the plan by the same band: a group that would exceed the admission maxima is a sibling wish, not a bigger group.

## Rules

- The objective is frozen: no stage re-asks it, narrows it, or widens it
- No vague tasks ("improve everything") — every task must be testable
- The executor edits only the declared file set; a diff that leaves it is blocked
- OUT scope must contain at least one concrete exclusion
- Merge, `SHIPPED`, promotion and worktree removal stay with the operator
